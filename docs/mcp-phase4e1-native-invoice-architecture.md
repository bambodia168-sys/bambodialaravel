## 2. Architectural decision — first release: order-linked commercial invoices only

Introduce a native Laravel invoice aggregate, reused by web UI and MCP adapters. Not a new checkout, gateway, receipt, settlement engine, tax system or stand-alone accounting package. An invoice is a request/document for payment; an order is the purchase and fulfillment record; payment is verified collection; receipt is evidence; settlement/refund/payout/recovery remain in existing native records. Preserve existing checkout, gateway, fulfillment, receipt URL/QR, licenses, analytics and all 38 MCP definitions unchanged.

First increment deliberately limits to one invoice aggregate per existing seller-owned USD order (unique FK for lifetime), distinct active seller and buyer, order status awaiting_payment, positive total, approved participant and commerce gates. No free, cancelled, refunded, already-completed order creation in v1; no backdating or bulk migration of historical orders. Existing invoices continue to reflect later source state. No new order from invoice, no standalone external customer, no off-platform payment or invoice-to-milestone billing; a future contract/milestone extension must establish an authorized payment linkage, allocation, no double-billing and accounting requirements first. Contract acceptance does not equal payment.

Issuer is marketplace seller and recipient is order buyer, derived from order ownership, never arbitrary IDs. Do not assume Bambodia itself is the legal seller of every order. Before issuance enablement, obtain explicit owner/accounting/legal review of seller identity, billing fields, invoice numbering, required taxes, retention, corrections and local jurisdiction requirements. No assertion of tax/VAT compliance; no invented tax rates/IDs or automated tax computation. Label drafts non-issued and not a tax invoice. First delivery is draft-only; issue and void are design states behind separate disabled feature and future authorized release. No email or notifications during draft creation/edit/discard. A distinct approved issuance phase is required even for web UI; no MCP issuance in initial registry.

## 4. Document lifecycle and reconciliation

Document status and financial collection state are distinct. draft -> discarded (terminal, no hard-delete or number), or draft -> issued (future approved UI only); issued -> void (future separate explicit authorization and legal review; cannot void collected/refunded or active payment obligation without approved correction workflow). No reissue/replacement of discarded or void invoices in v1; future revision/credit-note policy needed. Draft invisible to recipient, including lists/summaries; discarded issuer-only. Issued and void visible to both participants when future issuance is enabled. No public lookup by UUID/number; private authorized print/view only, no-store and noindex, no tokenized public invoice URLs in v1.

Payment state is computed read-only from authoritative order and payment records, not invoice status or user flags: awaiting_payment + no verified live payment = unpaid (active attempt does not equal paid); completed + positive matched source total/currency + explicit live paid attempt with settlement ref = paid; refunded + verified original payment and native confirmed full-refund evidence = refunded, not unpaid; cancelled with no verified payment = cancelled; inconsistent/missing source, ambiguous multiple verified paid attempts, mismatched parties or amounts = review_required and no collectable balance asserted. Zero orders excluded. Do not infer partial payments; none implemented. For an issued valid unpaid invoice, due_on < current business date can derive overdue; due date never changes checkout behavior. For paid/refunded/cancelled/void/discarded/draft do not count issued outstanding receivable; for review_required return null and separate count. Draft may show source order status as context only. No invoice action marks paid, changes order status, triggers payment, grants delivery, creates receipt, changes refund or payout, or retries email. Existing native buyer checkout/payment controls remain the only collection path.

## 5. Precision, authorization, API privacy

Money as canonical decimal strings at boundary, integer cents or exact decimal library internally (no floats), DECIMAL(12,2) matching native max 9999999999.99, reject exponent, extra scale, sign, negative, overflow and currency mismatches; one currency per invoice, no FX, no subtotal/discount/tax manipulation. Amounts derived server-side from locked order, checked every issuance/collection view. Group summaries by currency and document/payment state, no mixed currency sums, no join multiplication; no invoice totals added to existing paid-order revenue (avoid double-count). Explicit basis and window, as-of date UTC and display timezone, separate draft totals, issued totals and unpaid/overdue/review-required counts.

MCP: existing authenticated active super_admin, resource/audience and scopes mcp:use (mapped internal mcp.read), mcp.write additionally for WRITE; existing global MCP feature/WRITE gates, commerce_orders capability and new invoice feature flag (default OFF) / invoice_write flag (default OFF). Existing 38 definitions byte-for-byte compatible; feature off exposes no invoice definitions, read-only exposure adds four, write enabled adds three; authorization enforced in handler even if advertised. No OAuth expansion or account elevation. Native web: existing active seller/creator capability and exact source seller ownership for draft writes, recipient only issued/void read; no global administrator impersonation or override in first increment. Verify role/status/participant in transaction, not request fields. Recipient never sees draft/discarded. Cross-tenant/missing/unauthorized/ineligible uniform not-found response; scoped query before lookup/aggregation; whitelist outputs. No internal user IDs, contact addresses/emails, tax IDs, memo/private notes, payment/gateway identifiers, proof/storage paths, QR secrets, tokens, audit payload, full invoice PDF or arbitrary URLs in MCP. Bounded descriptions from order listing snapshot may contain user-generated text: treat as untrusted data, escape HTML, never interpret as instruction. No arbitrary search over sensitive fields. UI may show authorized required billing details only after policy review; no unverified user-provided tax data.

## 7. Transaction contract

Native service methods share one authorization path, exact schema, source/invoice HMAC version and mutation logic for UI and MCP. Source preview token includes locked order identity, participant IDs, original title/price/currency/status, verified payment summary and existing invoice identity/revision; invoice token includes canonical line state, dates, status, participants, source state and monotonic revision. Purpose-separated HMAC-SHA256 (APP_KEY); no raw state hash or secret returned. Consistent lock order after review of native payment lock ordering: actor (MCP policy), source order, relevant payment rows sorted by ID, invoice parent, lines sorted, ledger entry, future sequence only on issue. Payment handler must not be changed or acquire invoice locks in v1; concurrency acceptance verify order-first compatibility and bounded deadlock retry (max 3). Do not rely on unlocked preview. Authorize current actor/resource even on replay. Canonicalize validated args (including distinction between omitted and null where applicable); check prior actor/request UUID before stale-version rejection to return identical accepted result on authorized replay, different payload/tool/resource conflict; new request with stale token rejected, no blind retry. Unique source FK prevents second invoice from a different UUID. If replay after discard/paid source, revalidate actor and participant ownership and safely return original minimal receipt; do not reexecute or bypass current authorization. For an unchanged due date either explicitly reject no-op or return recorded no-op receipt according to a documented deterministic rule; recommendation reject no-op before mutation. Native allowlisted audit event and MCP event linked to ledger in same transaction. No external effect; no draft notification/outbox rows. Late exception rolls back all domain, ledger and audit changes. No secrets or submitted payload in logs. If future issue enabled: transactional immutable snapshot + sequence + audit + one recipient notification using native AccountNotification and EmailOutbox dedup key with approved template, after separate delivery review; no external send within transaction.
